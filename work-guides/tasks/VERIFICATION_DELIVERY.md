# 검증·빌드·배포·복구

[작업 선택표](../DEVELOPMENT_GUIDE.md)에서 이 작업에 해당할 때 읽는다. 다른 작업 문서를 전부 읽을 필요는 없지만, 변경이 다른 경계에 영향을 주면 해당 문서를 추가한다.

## 검증은 필요한 만큼 정확하게 한다

검증 선택 질문: **이 검사가 통과해도 사용자가 겪은 문제가 그대로 남을 수 있는가?** 그렇다면 최종 경계의 증거를 보완한다. 더 많은 테스트를 무조건 실행하는 것은 해법이 아니다.

| 변경 종류 | 우선 검증 | 확대가 필요한 경우 |
| --- | --- | --- |
| 문서·문구 | 의미, 중복, 링크, 변경 범위 | 실행 스크립트나 정책 계약이 문구를 참조할 때 |
| 계산·변환·정책 | 해당 함수의 경계값과 실패 재현 | 공용 규약·저장 형식이 바뀔 때 |
| 화면·입력 | 실제 렌더링과 해당 조작 흐름 | 공용 컴포넌트, 플랫폼별 입력 차이가 있을 때 |
| 프로세스·API·저장소 | 경계를 건너는 통합 테스트 | 권한·취소·동시성·복구 경로가 영향을 받을 때 |
| 설치·업데이트·배포 | 생성된 산출물과 설치된 실행 경로 | 구버전 마이그레이션, 재시작, 공개 전달 경로가 바뀔 때 |

- 선택한 검사와 이유를 짧게 기록한다. 이미 유효한 증거가 있으면 관련 코드·의존성·환경 변화 여부를 확인하고 재사용 범위를 명시한다.
- 같은 상태에서 같은 테스트를 반복 실행하지 않는다. 테스트 안에서 이미 발견된 다른 테스트 묶음을 다시 실행하는 중복 래퍼를 만들지 않는다.
- 변경과 무관한 전체 테스트·빌드·배포·원격 조회는 기본 실행하지 않는다. 영향 범위가 넓거나 필수 릴리스 조건에 해당할 때만 확대한다.
- 모의 테스트는 로직 격리에 사용한다. 실제 권한, 운영 규칙, 브라우저 입력, 설치된 바이너리, 실기기 동작을 증명한다고 주장하지 않는다.
- 소스 문자열 존재 여부만으로 기능 완료를 판정하지 않는다. 이런 검사가 필요한 구조 조건을 보호한다면 테스트 코드와 운영 코드를 구분하고 목적을 좁힌다.
- 실패하면 원인을 확인한 뒤 수정된 부분만 다시 검사한다. 일시적 외부 실패도 조건을 확인하고 제한적으로 재시도한다. 통과할 때까지 반복하지 않는다.
- 검사 오탐과 제품 결함을 구분한다. 불필요한 검사·중복 실행은 제거하되 실제 회귀 조건, 보안 조건과 미완료 증거는 지우지 않는다.
- 증거에는 명령 또는 조작, 대상 버전·환경, 결과, 남은 범위를 남긴다. 테스트 개수나 체크 표시를 품질 자체로 취급하지 않는다.
- 새로운 자동검사는 반복되는 의미 있는 실패를 안정적으로 검출하고 유지 비용보다 이득이 있을 때 추가한다. 지침 문장이 존재하는지만 검사하는 새 자동 계층을 기본으로 만들지 않는다.

## 빌드·배포·설치를 구분한다

- `수정됨`, `소스 검증됨`, `빌드됨`, `배포됨`, `설치 후 확인됨`을 구분해서 보고한다. 커밋·푸시·HTTP 성공·연결 성공이 다음 단계까지 증명하지는 않는다.
- 빌드와 배포는 사용자 승인 범위 및 프로젝트 정책 안에서 수행한다. 문서나 작은 로직 변경을 이유로 무관한 패키징을 반복하지 않는다.
- 배포 대상 코드·설정·버전·아키텍처와 산출물을 연결한다. 클라이언트·서버·네이티브 모듈을 섞거나 오래된 빌드 결과를 새 수정본으로 배포하지 않는다.
- 업데이트는 출처·서명·체크섬·대상·버전을 검증하고 실패하면 기존 동작과 데이터를 보존한다. 서명 키 분실을 검증 해제나 무단 키 교체로 해결하지 않는다.
- 위험에 따라 특정 장비·시험 그룹·제한된 비율부터 배포한다. 명시적 대상 제한이 실제로 지켜지는지 확인하고 공개 최신 버전과 시험 배포를 혼동하지 않는다.
- 시험 배포도 필수 보안 조건을 지켜야 한다. 남은 기능 검증을 밝히고, 확대 조건·중단 기준·복구 방법을 준비한다. 필수 검사를 낮춰 정식 배포로 포장하지 않는다.
- 공개 후에는 실제 다운로드·업데이트 경로와 설치된 버전·기능을 확인한다. 파일 업로드만으로 사용자에게 전달됐다고 판정하지 않는다.
- 부분 게시·실패 상태는 명확히 드러낸다. 사용 중인 자산의 삭제·덮어쓰기·태그 변경은 영향과 승인 범위를 확인한다.

## 실패는 복구하고 재발 원인을 남긴다

- 사용자 영향이 있는 실패에서는 추가 손상을 먼저 막는다. 증거를 보존하고 알려진 정상 상태로 복구할 수 있는지 판단한다.
- 증상, 직접 원인, 놓친 검증, 영향 범위, 수정, 재현 증거와 남은 위험을 구분해 기록한다. 원인이 미확인이면 추정을 확정 원인으로 바꾸지 않는다.
- 실제 장애와 반복되는 개발 실수에는 지속 가능한 회귀 방지책을 둔다. 사소한 일회성 오타마다 새 정책·테스트·긴 사고 문서를 만들지는 않는다.
- 과거 기록은 당시의 사실이다. 현재 권한·버전·구조·완료 상태로 재사용하지 않는다. 과거의 잘못된 판단은 삭제로 숨기지 말고 정정 근거를 추가한다.
- 로그는 실패 단계와 상관관계를 찾을 수 있어야 하며 크기·보존 기간에 한도를 둔다. 비밀정보와 불필요한 개인정보는 남기지 않는다.
