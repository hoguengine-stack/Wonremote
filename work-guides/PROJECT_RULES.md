# 현재 저장소 전용 조건

이 문서는 기존 구현 프로토콜과 품질 가드레일에 있던 제품 전용 조건을 보존한다. **범용 지침서가 아니며 다른 프로젝트에 자동 적용하지 않는다.** 현재 작업 상태는 원본 계약과 사고 기록에서 별도로 확인한다.

## 적용 관계

- 공통 절차: [범용 개발 지침서](DEVELOPMENT_GUIDE.md).
- 저장소 필수 계약·요청 예산·커밋·배포 검사: [PROJECT_POLICY.md](PROJECT_POLICY.md). [AGENTS.md](../AGENTS.md)의 지정 시점에 반드시 적용하며, 이 문서 통합으로 기존 필수 검사를 생략하지 않는다.
- 실제 제품 목표와 성능 기준: [제품 계획](../ZOOK_REPLACEMENT_PLAN.md). 계획의 과거 상태 설명을 최신 코드 상태로 간주하지 않는다.
- 현재 진행 상태와 남은 검증: [작업 계약](../CHANGE_CONTRACT.json).

## 실행 경로와 지원 범위

- 고정 테스트 장비(사용자 지정): `82220F6D`, `59F19451`, `1D42C9F9`. 테스트 대상 지정은 공개 배포나 해당 기기의 재부팅·설치·업데이트 실행 승인을 대신하지 않는다.

- 관련 변경에서는 Viewer/Agent, Windows 32/64비트 호스트, Firebase/로컬, 개발/패키지/설치, 최초 설치/업데이트/재시작 중 영향을 받는 경로를 구분한다. 각각 실행 검증·검토·비대상과 이유를 기록한다.
- 현재 승인된 Windows 릴리스 페이로드는 x86이다. 32비트와 64비트 호스트에서 지원되는 x86 설치 경로를 검증한다. 별도 x64·포터블 자산으로 임의 교체하지 않는다.
- UI에서 백엔드, 네이티브 모듈, 리소스 패키징, 설치된 프로세스까지 실제 경로를 확인한다. 개발 경로의 성공이 설치 환경의 성공을 대신하지 않는다.
- 설정 보존, 업데이트 잠금 정리, 복구 로그와 구버전 호환성은 관련 변경의 검증 범위에 포함한다.

## 릴리스 및 업데이트

- 사용자 승인 Viewer 단독 배포: Viewer만 새 버전으로 빌드·서명하고 기존 공통 GitHub `latest`·Agent 매니페스트·배포 정책은 보존한다. Viewer 전용 `/updates/viewer-latest.json`은 기존 공개키와 V1/V2 서명을 유지하며 설치 파일 URL은 불변 버전 태그를 사용한다. Viewer 단독 태그는 `make_latest=false`, Agent 설치본·교체본은 포함하지 않는다. 기존 Viewer의 이전은 기존 서명된 명시 대상·유효기간·유휴 검사 정책만 사용한다. Android도 Viewer만 올리고 Agent·제어 모듈의 기존 서명·바이트·발견 정보를 검증해 보존한다. 이후 함께 배포하면 다음 공통 버전과 공통 `latest`, Viewer 전용 발견 파일·다운로드 별칭을 함께 갱신한다. 아래 두 제품 동시 버전·자산 조건은 전체 배포에 적용하며 단독 배포를 위해 신뢰·소스·해시·서명·회귀 게이트를 면제하지 않는다.

- 배포 전 필수 검증과 미완료 항목은 현재 계약을 따른다. 근거 없는 준비 상태 변경이나 검증 수준 하향으로 게시하지 않는다.
- 릴리스 빌드는 정확한 `main`의 `Prepare WonRemote v...` 준비 커밋 또는 승인된 수동 워크플로에서 시작한다. 빌드 전 수동 태그 생성과 태그만으로 빌드를 시작하는 방식은 사용하지 않는다.
- 빌드 작업 영역은 해당 준비 커밋과 일치해야 하며 산출물은 새로 생성한다. 이를 맞추려고 사용자의 미커밋 변경을 삭제하거나 임시 작업 영역에 연결된 원본·서명 키를 정리하지 않는다.
- 승인된 한 태그에는 `WonRemote-Viewer-Setup.exe`, `WonRemote-Agent-Setup.exe`, 서명된 업데이트 매니페스트가 함께 있어야 한다. 산출물 역할·아키텍처·버전·크기·SHA-256·서명·공개키·URL을 일치시킨다.
- Agent 파일 교체 업데이트를 배포할 때는 같은 빌드의 `WonRemote-Agent-Update.exe`도 함께 검증·서명·게시한다. 구버전의 `agentWindows`와 최초 설치·복구용 `agentInstallers`는 서명된 Setup을 유지한다. `agentFileUpdates`만 전용 교체본으로 서명하며, 새 네이티브 호스트가 보호된 설치·등록·broker를 확인한 경우에만 선택한다. 선택한 교체본의 서명 오류는 Setup으로 숨기지 않고 실패한다. `/download/agent`와 x86 별칭은 Setup을 유지한다. 구 설치 경로 이전과 실제 재접속 증거 없이 전 장비 적용을 보장하지 않는다.
- 업데이트 매니페스트 서명과 실행 파일의 Authenticode 서명은 다른 검증이다. 현재 Authenticode 정책과 실제 서명 여부를 별도로 보고하고, 업데이트 신뢰 검증을 없애지 않는다.
- 관련 Firebase 별칭 `viewer`, `agent`, `viewer-x86`, `agent-x86`이 동일한 검증된 두 설치본으로 연결되는지 확인한다. 소스 푸시만으로 공개 배포를 완료했다고 보고하지 않는다.
- 설치형 Viewer의 수동 업데이트 확인은 네이티브 서명 검증 경로를 사용한다. WebView의 GitHub 자산 직접 fetch로 이 검증을 대체하지 않는다.
- 구버전 Viewer/Agent에서 업데이트, 재시작, 설정 보존, 대상 버전과 복구 동작을 확인한다. 부분 게시나 실패를 `latest` 정상 상태로 취급하지 않는다.
- 미완료 구현을 버전 증가로 완료한 것처럼 처리하거나, 비판을 롤백 지시로 해석하지 않는다. 요청된 구현과 해당 소스 검증을 마친 뒤 승인된 빌드에 새 버전을 배정하며 기존 공개본과 지정 시험본보다 높게 맞춘다. 설치·실장비 검증용 빌드는 정식 게시와 구분하고, 실제 배포에는 기존 필수 검증·게이트를 그대로 적용한다. Android Viewer·Agent·제어 추가모듈도 같은 버전과 기존 서명으로 함께 준비한다. APK 생성 후 프런트를 빌드하거나 검증된 다운로드 파일을 동기화하고, `mobile/android/create-update-manifest.mjs --verify-hosted`로 실제 Hosting 산출물 일치를 확인한다. PC만 준비한 상태를 전체 배포 준비 완료로 보고하지 않는다.
- 이미 공개된 자산 삭제·교체는 명시적 승인 없이 하지 않는다. 서명 키가 없으면 기존 설치본의 신뢰를 유지할 수 있는 복구 또는 승인된 전환 계획이 필요하다.

## Windows 및 로컬 권한

- 일반 사용자 쓰기 가능 경로의 바이너리를 최고 권한으로 예약 실행하는 구조를 사용하지 않는다. 보호된 설치 경로·파일 권한·서비스/작업 주체·호출자 검증을 함께 확인한다.
- 일반 화면, 잠금, 자격 증명 화면, SYSTEM 창, 복귀 경로는 다른 권한·데스크톱 경계다. 에이전트가 살아 있다는 사실과 실제 픽셀·입력 처리를 구분한다.
- 번들 Node 경로는 정규화된 리소스 루트에서 만든다. Windows verbatim 경로 접두사가 Node 실행 파일·스크립트·재시작·환경 인수로 넘어가지 않게 한다.
- 외부 원격 프로그램 비교는 허용된 사용 관찰과 공개 API 중심으로 수행한다. 이 프로젝트의 기존 외부 제품 바이너리 디컴파일·패치·비공개 프로토콜 및 UI 자산 복제 금지 조건을 유지한다.

## 성능 해석

- 최저 목표 장비, Worst-Case 조합, 지연·CPU·메모리 수치는 제품 계획의 해당 절을 단일 기준으로 참조한다. 서로 다른 문서에 복사해 기준을 늘리지 않는다.
- RGB565 전처리, 캡처·압축 내부 시간만으로 전체 프레임 전송 성능이나 실사용 원격제어 성능을 주장하지 않는다.
- WebRTC와 대안 전송 방식은 실제 타겟 조건의 비교 결과로 판단한다. 하드웨어 인코더 사용 가능성을 장비 확인 없이 전제하지 않는다.
- 디코드 감지와 실제 표시 시점, 내부 지연과 `T_presented - T_start`를 구분한다. 고성능 장비 결과를 저사양 장비 증거로 대체하지 않는다.
- 과거 문서의 실장비 검증 우선순위 변경은 성능 합격 증거가 아니다. 저사양 및 외부망 미검증 상태를 현재 결과와 분리한다.
